# Rice Leaf Severity Heatmap — Project Context

## Purpose

This is a **thesis prototype** for the paper *"A Web-Based Rice Disease Detection and Field-Scale Disease Pressure Estimation System Using SegFormer and Spatial Interpolation"*. It implements the **front-end spatial interpolation and heatmap visualization** component, plus a **Python inference backend** (`backend/`) that serves the trained 2-stage SegFormer models under `segfomer_model/`.

The target users are **Filipino rice farmers** working in the field with smartphones. The app must be mobile-first, touch-optimized, and functional on mid-range Android devices over cellular connections.

## Workflow (Strict 3-Step Process)

The app enforces a linear, sequential workflow:

1. **Draw Boundary** — User draws a closed polygon on a satellite map to define their rice field.
2. **Sample Plants** — User captures/uploads photos for up to 50 georeferenced plant nodes. **A node is one rice plant, not one photo**: a rice leaf is long enough that a single leaf often needs several frames, and field practice samples several leaves per plant, so each node holds 1–`MAX_IMAGES_PER_SAMPLE` photos pooled into one severity value (PDLA %). Every photo passes through a mandatory alignment crop against one static framing rectangle before it's analyzed — see Sample Acquisition Methods below.
3. **Generate Heatmap** — IDW interpolation computes disease pressure for all un-sampled points inside the boundary, rendered as a green→red color overlay clipped to the polygon.

Steps cannot be skipped. The user must complete each step before advancing.

## IDW Parameters

Tunable constants (power, cell size, max cells) and the formula/variable definitions live as documented constants in `src/constants/constants.js` — read there, not here.

IDW runs in a **Web Worker** (`idwWorker.js`) to avoid freezing the UI. It interpolates **one channel per disease class in a single pass** — the point-in-polygon test dominates the per-cell cost and is identical across diseases, so one multi-channel worker run beats one run per disease. The worker's output is one `Float32Array(rows × cols × channels)`, channel-major, sliced into per-disease `Float32Array` views on the main thread (`idwInterpolation.js`) with no copy. The interpolated quantity is still continuous float PDLA % — banding into IRRI SES happens strictly downstream, for display, and never touches the interpolation itself.

**IRRI SES banding.** `src/utils/sesScale.js` maps a continuous PDLA % to the IRRI Standard Evaluation System's 0–9 scale, using two breakpoint tables (`SES_BREAKPOINTS_SHARED` for Bacterial Blight/Brown Spot, `SES_BREAKPOINTS_BLAST` for Leaf Blast — its lesions expand faster, so it reaches SES 9 at 65% PDLA instead of 75%) in `constants.js`. Rendering uses a *continuous* SES value (`pdlaToSesContinuous`), not the rounded integer, so the heatmap surface stays visually smooth while `Math.floor()` of that value is always the exact IRRI class — this floor invariant is enforced even exactly on a band's own boundary (see the epsilon note in `sesScale.js`).

**Per-disease attribution.** `diseaseSeverity` is built by grouping photos by diagnosis, not pixels — see Plant-Level Pooling below for the pooling formula and the exact-sum property. There is no separate per-disease gate: each photo was already censored once, by the backend, before it can carry a non-Healthy diagnosis at all; a second, independent gate on pooled per-class pixel counts was the old model (see `aggregateSample.js`'s module docblock) and is gone. Even a Healthy-diagnosed photo still contributes its leaf area to every disease's shared denominator — it just contributes zero to any numerator.

**General Threat layer.** `sesGrid.js`'s `maxSesGrid` takes the per-cell `MAX()` across every disease's continuous SES grid (`floor(max(a,b)) === max(floor(a), floor(b))`, so maxing the continuous values before flooring is equivalent to the spec's `Math.max()` over integer SES classes, and renders just as smoothly). **General is not a percentage** — it's the highest disease class present at a point — and must never be displayed or described as one; `ColorLegend.jsx` hides the PDLA breakpoint row for this layer specifically because it has none.

Switching the active layer (`heatmapLayer` state in `App.jsx`) never re-runs the worker — `sesLayers` is a `useMemo` over the one `computeIDW` result, so layer switches are pure re-renders.

**LOOCV Validation.** `src/utils/loocv.js`'s `runLOOCValidation(dataset, power, options)` and `optimizePowerParameter(dataset, candidatePowers, options)` measure interpolation accuracy by Leave-One-Out Cross-Validation: each committed plant is held out in turn and its severity re-predicted from the other N−1 via the same estimator the heatmap uses, then compared to what was actually measured. That shared estimator is `src/utils/idwCore.js`'s `idwEstimateInto()` — extracted verbatim from `idwWorker.js`'s per-cell loop (the worker now just calls it) so LOOCV can never silently drift from validating a different model than the one that paints the map; a `skipIndex` parameter is the only addition. `idwInterpolation.js`'s `resolveDiseaseChannels(samples)` is the other shared piece — the same disease-presence/ordering logic `App.jsx`'s `handleGenerateHeatmap` uses to pick heatmap layers, so LOOCV scores exactly those channels, never a parallel selection.

Reachable three ways: the "Export LOOCV Validation" button at the bottom of the Sample History sidebar (Heatmap step, gated on `samples.length >= MIN_SAMPLES`) downloads a residuals CSV and a summary+sweep JSON via `exportLoocv.js`, the only DOM-touching file in the feature; `window.__loocv` in dev builds (`import.meta.env.DEV`-gated, `App.jsx`) exposes `run`/`sweep` bound to live `samples` state for console experimentation; and `npm run loocv -- <path> [--powers=1,1.5,2,2.5,3]` (`scripts/loocv.js`) re-runs offline against a downloaded JSON, plus `npm run loocv -- --selftest` for refactor-parity and analytic checks. `loocv.js` itself is pure and Node-runnable, same discipline as `sesScale.js`/`aggregateSample.js` (explicit `.js` extensions on relative imports).

Errors are reported in PDLA percentage points on the continuous value (MAE, RMSE), not banded SES — matching where interpolation actually happens; a `channels[label].degenerate` flag marks a channel whose held-out actuals are all equal (most often a disease absent from every node), since a constant target scores a trivially perfect MAE/RMSE that reflects zero variance to predict, not measured skill, and must never be quoted as a result. See Known Limitations below for what LOOCV does and doesn't validate.

## ML Inference Pipeline

`src/services/mockMLService.js` (name kept for import stability — the only importer is `App.jsx`) calls the real 2-stage SegFormer API at `ANALYZE_ENDPOINT` (`src/constants/constants.js`), proxied by Vite to a FastAPI server.

**Pipeline** (`backend/inference.py`, class `TwoStagePipeline`):
1. **Phase 1** (`segfomer_model/phase1_leaf_isolation/`) — binary SegFormer-B1, leaf vs. background.
2. **Leaf Focus Module** — pure numpy/PIL: mask × RGB blacks out background, crop to the mask's padded bbox.
3. **Phase 2** (`segfomer_model/phase2_disease_segmentation/`) — 5-class SegFormer-B1 on the cropped leaf: `background, healthy_leaf, leaf_blast, brown_spot, bacterial_blight`. **No Sheath Blight class exists in the trained checkpoint** — class ids are read from the model config / `deployment_metadata.json` at runtime, so a future re-trained model with more classes drops in without code changes.
4. **PDLA** = `100 × disease_pixels / phase1_leaf_pixels`, per `deployment_metadata.json`'s `pdla_formula`.

**Response contract** (unchanged from the original mock): `{ diseaseDetected, severity, diseaseName, confidence }`. `severity` is now a real float PDLA percentage — display sites use `.toFixed(1)`. A `status: "no_leaf_detected"` result and any thrown fetch error both set `analysisError` on the draft sample in `App.jsx`, and `canAddSample` blocks commit until it's clear — a failed or leafless analysis must never inject a fabricated severity into the IDW grid.

The response also carries a `masks` block — a **display artifact, not diagnostic data**: PDLA is computed from the full-resolution arrays before `masks` is ever built, so nothing about the number depends on it. `null` on the `no_leaf_detected` path and on any preview-encoding failure; `mockMLService.js` passes it through unchanged (`return res.json()`). See "Mask Previews" below.

### Mask Previews

Every `ok` response carries `masks: { leaf, disease, size_wh, source_size_wh, class_order, palette, class_names, leaf_color }` — small PNG data URLs of the Phase 1 leaf mask and the Phase 2 disease mask, for `MaskInspectorModal.jsx` (opened from a photo tile in `SamplePanel.jsx`/`SampleSheet.jsx`, or a photo row in `SampleHistorySidebar.jsx`, via one `App.jsx`-owned callback). Raw masks, not overlays — Phase 1 is white-on-black binary, Phase 2 is flat per-class colors on black, showing exactly what each model emitted.

**Co-registration.** Phase 2 runs on the cropped leaf (`crop_h × crop_w`), but the mask shipped to the UI is pasted back into the full WORK-space canvas (`full_labels[y0:y1, x0:x1] = restricted`, `background_id` elsewhere) before encoding, using the same `y0/y1/x0/x1` `_pad_bbox` already computed — never the `diagnostics.crop_bbox_xyxy` reported separately, which is rescaled to ORIGINAL coordinates and rounded for a different purpose and would drift a pixel per edge here. This is what makes all three viewer panes (aligned photo, Phase 1, Phase 2) share one coordinate grid. Pane 1 (the aligned photo) is only pixel-identical to that WORK array because every photo reaching `/api/analyze` is a Canvas2D crop from `cropToStencil.js` carrying no EXIF tag — a consequence of the mandatory alignment step, not a guarantee `analyze()` makes on its own.

**NEAREST resampling is a correctness requirement, not a quality choice.** Class ids are nominal, not ordinal — any interpolating filter averages ids, e.g. blending `leaf_blast` (2) with `bacterial_blight` (4) produces `brown_spot` (3) along every lesion boundary, a diagnosis the model never made, painted onto the one view whose entire purpose is showing what it actually predicted.

**`MASK_PREVIEW_MAX_SIDE = 256`.** Every app-produced photo is exactly `ALIGN_OUTPUT_WIDTH/HEIGHT` (1024×1024) and `DEFAULT_MAX_SIDE` (2048) never shrinks it, so WORK space is always 1024² in practice — 1024/256 = 4 exactly, an integer NEAREST decimation with no moiré. Because these are flat-color label images, a 256px preview upscaled to a phone-sized pane is visually indistinguishable from a native one — there's no quality reason to go larger, only cost (worst case ~500 committed photos × ~10 KB ≈ 5–9 MB; see Blob lifetime below).

**Palette.** Resolved at load time off `id2label`, the same pattern as `disease_display_names` — `background` is colored by class id (not the literal label, since a retrained checkpoint could name it differently), the shipped disease/healthy classes get fixed hex colors, and any class the static table doesn't cover gets a deterministic golden-ratio HSV fallback. This is what keeps the "a re-trained model with more classes drops in without code changes" property true for the mask viewer and its legend too — `class_order`/`palette`/`class_names` in the response are what the legend renders from, with no client-side class knowledge. These colors encode class identity only — no severity meaning, and unrelated to the green→red SES ramp in `sesScale.js`.

`_warmup()` and `backend/probe_fill.py`'s repeated `analyze()` calls pass `include_masks=False` — they only need the numeric measurement, and the warmup dummy (a flat green square) gets masked edge-to-edge per this file's own leaf-plausibility probe table, so it would otherwise pay the full encode cost on every process start. `analyze()`'s default is `include_masks=True` specifically so `backend/server.py`'s `run_in_threadpool(pipeline.analyze, raw)` call needs no change — Starlette forwards positional args only.

No new dependency: mask encoding uses only `base64`/`colorsys` (stdlib) plus the `PIL`/`numpy` already imported.

### Plant-Level Pooling

`/api/analyze` stays one image per request; each photo comes back with its own single diagnosis — `diseaseLabel`, the dominant disease class by pixel count, already gated on that photo's own disease fraction (`healthy_leaf` if it doesn't clear the gate). `src/utils/aggregateSample.js`'s `summarizePlant()` takes that diagnosis at face value: a photo's WHOLE PDLA — every disease pixel it has, not just its winning class's — belongs entirely to its one diagnosis. Photos are grouped by diagnosis and pooled over the plant's whole leaf area:

```
diseaseSeverity[label] = 100 × Σ disease_pixels (photos diagnosed `label`) / Σ leaf_pixels (every usable photo)
severity               = 100 × Σ disease_pixels (every diagnosed photo)   / Σ leaf_pixels (every usable photo)
```

Both sums are of raw pixel counts, **not a mean of per-photo percentages** — pooling weights each photo by the leaf area it actually captured, so a close-up of one lesion doesn't weigh as much as a wide shot of clean tissue just because both are "one photo". `severity`, the plant total, uses the same shared denominator as every `diseaseSeverity[label]`; because every photo's whole PDLA lands in exactly one disease's numerator, `Σ diseaseSeverity` sums EXACTLY to `severity` (barring independent 2dp rounding of each term).

**A plant is not forced down to one disease.** A rice hill has multiple tillers and leaves, and it is biologically normal for one part to carry Leaf Blast while another carries Brown Spot — one photo diagnosed Leaf Blast and another diagnosed Brown Spot means the plant carries both; a third photo also diagnosed Brown Spot pools into that same group. `summarizePlant()` derives `diseaseFindings` — every disease at least one photo was diagnosed with, each with its own pooled PDLA %, the count of photos behind it, and sorted descending — from the same `diseaseSeverity` object the heatmap already reads, so there is one source of truth. `diseaseName`/`diseaseLabel` (the single dominant label — the highest-pooled `diseaseFindings` entry) still exist and still drive things that need one label — the history row title, the marker popup's fallback text — but `diseaseFindings` is the labeled, multi-disease list the Sampling screen actually renders, at plant level (`SamplePanel`'s summary). Each PHOTO, by contrast, still shows exactly one diagnosis — its whole PDLA, labeled with its dominant disease, same as the original single-image contract — via `photoDiagnosis` in the same file; multi-disease reporting is a plant-level concept built by grouping single-diagnosis photos, not a per-photo one. Per-photo diagnosis (`severity`, `diseaseName`, `diseaseLabel`) is retained on the committed sample's `images[]`.

**No plant-level confidence is claimed.** Each photo's confidence is a mean softmax posterior conditioned on *that photo's* winning class, which may differ from the plant's, so combining them yields a number with no referent. The per-photo range is displayed instead.

A photo that fails or returns `no_leaf_detected` is **excluded, not fatal** — it contributes zero to both sides of the ratio, so it cannot fabricate a severity, and the plant is still savable as long as one photo produced a measurement. If every photo fails, `severity` is `null` (never `0`) and the plant cannot be committed.

**Weighting caveat for the write-up:** every photo — camera or gallery — now passes through a mandatory alignment crop (`ImageAlignmentModal.jsx` → `cropToStencil.js`) before it reaches analysis, at one fixed square output resolution for every photo (`ALIGN_OUTPUT_WIDTH/HEIGHT` in `constants.js`, 1024×1024 — square so the SegFormer preprocessor's own 512×512 resize is isotropic, unlike the old non-square crop). That resolution sits under the backend's `DEFAULT_MAX_SIDE`, so `_downscale` is a no-op for every photo — the dominant source of scale variance from output *resolution* (a close-up photographing 4× more effective resolution than a wide shot of the same tissue) is gone.

Resolution alone doesn't fix *magnification*, though: two photos of the same blade taken from different distances still land at different pixel scales unless the farmer has something physical to align against. The frame now also carries a static blade-width guide — a dashed vertical rail at `ALIGN_GUIDE_WIDTH_FRACTION` (20%) of the frame's width, spanning its full height — that asks the farmer to fit the leaf's width to the rail, not past it. This targets a constant pixels-per-blade-width across every photo, which is what the pixel-count pooling actually needs to be comparable plant-to-plant, not just frame-to-frame. **It is guidance only** — nothing measures or enforces whether a given photo complies.

What's left: no physical scale reference is in frame, so pixel→mm² is still unknown; the weights are now blade-width-normalized, not calibrated to a physical unit. The residual assumptions are that blade width is roughly constant within a variety, and that the farmer aligned to both the static framing rectangle and the width guide by eye.

### Leaf Plausibility Guard

Phase 1 is a binary leaf/background segmenter with **no negative class**, so it cannot say "this is not a rice leaf". `no_leaf_detected` only fires on zero leaf pixels. Measured against synthetic probes, the dominant failure is the *opposite* of what you'd expect — a uniform surface gets masked edge-to-edge with high confidence:

| subject | `leaf_frame_fraction` | `leaf_mask_confidence` |
|---|---|---|
| textured soil | 0.003 | 0.52 |
| grey concrete | 0.295 | 0.56 |
| textured skin | 0.998 | 0.78 |
| blue sky | 0.9997 | 0.96 |
| dense green canopy | 1.000 | 0.99 |
| **leaf blade on soil** | **0.139** | **0.958** |
| well-aligned crop (design target) | **0.13–0.16** | — |

So the guard is a *band*, not a floor: `MIN/MAX_LEAF_FRAME_FRACTION` and `MIN_LEAF_MASK_CONFIDENCE` in `constants.js`. Thresholds live in the front end so they can be tuned without restarting a process that loads two SegFormers. **They are untuned heuristics from synthetic images** — re-measure against real field captures before quoting them.

**Post-crop note:** the six-row probe table above predates the alignment crop and no longer describes the input distribution this guard actually sees — every photo reaching it is now cropped exactly to the static framing rectangle's boundary, with no separate outer frame guaranteeing background margin the way the old per-region stencils did (each of those enclosed a small, fixed fraction of a larger box, so background survived regardless of how tightly the user filled the outline). Now, how much background survives depends entirely on how loosely the user centers their leaf in the box, per the on-screen instruction text. If well-aligned real photos start landing close to `MAX_LEAF_FRAME_FRACTION` (0.97), that is the first constant to revisit — the safety margin this guard used to get for free is now just a soft expectation, not a structural guarantee.

**Running the backend:** see the `run-backend` skill for setup steps and the conda/venv-shadowing gotcha.

## UI / UX Principles

These principles are actively enforced and must be maintained:

- **Mobile-first** — All touch targets ≥ 48px. The app is designed for field use on smartphones.
- **Heuristic evaluation** (Nielsen's 10) — Applied throughout:
  - Visibility of system status (live vertex counter, step indicator, loading progress).
  - Recognition over recall (all tool buttons have text labels + icons, not just icons).
  - User control & freedom (cancel drawing, edit/redraw boundary, manual GPS fallback).
  - Error prevention (disable "Continue" while drawing, point-in-polygon validation).
  - Match system & real world (natural language instructions, not technical jargon).
- **Geoman's default toolbar is hidden** — Custom themed buttons in the ActionPanel replace it.
- **Responsive stepper** — Mobile shows a compact pill (`Step 1/3 · Draw Boundary`), desktop shows full horizontal stepper. Breakpoint: 768px.
- **Mobile sampling uses a draggable bottom sheet** (`SampleSheet.jsx`) floating over a full-bleed map; desktop uses the side-by-side split. Both render the same `SamplePanel`, so a prop change lands on both surfaces at once.
- **Every photo's fate is legible from its own tile** — analyzing, failed, quality-flagged, or counted — so the farmer can see which shot to retake without parsing a summary. This is why the photo strip is a vertical list rather than a horizontal carousel: a carousel would hide the warning text.
- **Any full-viewport modal renders from `App.jsx` as a direct child of `.app`, never nested inside `SamplePanel`/`SampleSheet`.** `.sheet` carries a CSS transform (`translateY`), which establishes a containing block for `position: fixed` descendants per spec — a modal mounted underneath it would get dragged around by the sheet's own translate instead of staying pinned to the viewport. Two components now depend on this: `ImageAlignmentModal.jsx` and `MaskInspectorModal.jsx`. (The existing `.upload-lightbox` inside `SamplePanel.jsx` predates this rule and has the bug; don't copy it.) Both mounted-outside components also redeclare the `--upload-*` CSS custom property block themselves (`.align-overlay`, `.mask-overlay` in `App.css`) — those tokens are not in `:root`, only in the panel scopes a sibling-of-`.app` modal sits outside of.

## Sample Acquisition Methods

The app supports three ways to georeference a plant node:

1. **Camera capture** — an in-app live viewfinder (`CameraCaptureModal.jsx`) showing the camera feed under the same static framing rectangle and dashed blade-width guide `ImageAlignmentModal` draws (shared geometry via `useFramedStageSize.js`), so the farmer composes the shot against the guide live rather than only seeing it after the fact. Used only when `cameraSupport.js`'s `supportsLiveCamera()` is true at tap time (`window.isSecureContext` + `navigator.mediaDevices.getUserMedia` present) — over a non-secure context (e.g. the LAN `http://` address the Vite dev server prints for phone testing) it silently falls back to `<input capture="environment">`, which hands off to the OS camera app and uses the device's live GPS the same as before. The live viewfinder also falls back to that same input if `getUserMedia` itself fails at runtime (denied permission, no camera, camera busy elsewhere) — see the "Use system camera instead" button in `CameraCaptureModal.jsx`. Either path produces one plain `File` and reaches `handleImagesSelected` (`App.jsx`) identically; the live camera is guidance layered on top of capture, not a second capture pipeline — it still queues through `ImageAlignmentModal` like every other photo, per the "Neither Camera nor Gallery goes straight to the ML pipeline" paragraph below.
2. **Gallery upload** — `multiple`, so a plant's photos can be picked in one go. Parses EXIF GPS from the first *committed* file via `exifreader`.
3. **Manual Latitude/Longitude Input** — If no GPS is found or the GPS falls outside the boundary, the user types the coordinates. `DraftMarker` previews the pin live as they do.

**Neither Camera nor Gallery goes straight to the ML pipeline.** Every picked photo queues through `ImageAlignmentModal` — pan/zoom/rotate (coarse 90° steps plus a continuous ±45° straighten slider) and flip horizontal/vertical the leaf into one static square framing rectangle (matching the SegFormer preprocessor's own 512×512 input shape, so its resize is isotropic), the same shape for every photo, then crop to its boundary — before it becomes a draft image. Inside that rectangle, a dashed vertical guide marks 20% of the frame's width, full height: the on-screen instruction asks the farmer to fit the leaf's widest part to that rail without crossing it, giving a consistent blade-width-to-pixel scale across photos taken at different distances. **The guide is static visual guidance only — nothing detects or enforces whether the leaf actually fits it.** This is what makes `aggregateSample.js`'s pixel-count pooling scale-consistent, not just framing-consistent (see Plant-Level Pooling above); there is no path from either capture method to `/api/analyze` that skips it. A photo only becomes part of the draft, and only then starts analysis, once its crop is confirmed — see `useAlignmentQueue.js`. There is no re-align action: the original file isn't retained past a successful crop, so fixing a bad alignment means removing the photo from the strip and retaking it.

Framing feedback is severity-tiered, not one generic warning: a single `alert` object in `ImageAlignmentModal.jsx` (blocking > soft overflow > too-close, at most one shown) drives a badge over the viewfinder, the frame border color/pulse, and a promoted alert card in lockstep, so a hard block (`ALIGN_MAX_OVERFLOW_FRACTION` exceeded, "Use Photo" disabled) never looks like a soft advisory (the 25–40% overflow band, or zoomed in past `ALIGN_BLUR_WARN_SOURCE_WIDTH`) the way the old single `.align-warning` line did. The card always renders inside a fixed-height `.align-alert-slot` (empty when there's no alert) rather than being a conditional flow element, so mounting it — or switching between the blocking and caution copy, which are different lengths — never changes `.align-overlay`'s flex layout and never resizes the viewfinder underneath it; longer copy scrolls inside the band instead.

**The framing rectangle can legally hang off the source photo.** Fitting a close-up leaf to the blade-width guide often means zooming *out*, which is exactly what pushes the frame past the source image's edge — so the confirm gate (`getCropOverflowFraction` in `cropToStencil.js`) is a real clipped-area fraction, not a contained-or-not check, and blocks "Use Photo" only past `ALIGN_MAX_OVERFLOW_FRACTION` (40% of the frame's area). Below that, `cropAlignedImage` paints the uncovered part with `ALIGN_VOID_FILL_RGB` (flat black, `constants.js`) instead of rejecting the photo — PDLA only counts pixels inside the Phase-1 leaf mask, so a fill that reads as background is invariant to the ratio. That color isn't a guess: Phase 1 has no negative class and can misread a flat, uniform fill as leaf (this file's own probe table shows sky-blue scoring 99.97% "leaf"), so `backend/probe_fill.py` measured candidate fills — flat black, soil brown, soil-colored noise, blurred mirror-padding — against the real checkpoint, first on a 5-6 photo convenience sample (an earlier pass picked soil brown), then re-measured on 48 real, raw, unaligned rice-leaf photos spanning all 3 disease classes plus healthy, with genuinely complex backgrounds — other rice plants, unrelated shrubs, bare soil (2026-07-29). That larger run fixed a real bug in the probe script itself (it computed the leaf bbox via the EXIF-orientation-corrected `pipeline.analyze()` but painted the ring on an EXIF-uncorrected raw array — invisible on square crops, but a coordinate-space mismatch on any raw phone photo carrying an EXIF rotation tag, producing spurious "leaks" up to 27% that had nothing to do with any fill color) and reversed the fill-color pick: flat black's worst-case leak was 2.36% of the painted ring area, statistically tied with mirror-blur padding (2.37%) and well ahead of the earlier soil-brown pick (5.10% on this larger set). Black won over the tied mirror-blur candidate because it's the simpler implementation already in place, for no measured leak disadvantage. The cap itself — 40% — was re-measured on the same 48-photo set: mean PDLA drift from the void=0 reference stayed under 1 point at every measured void level (20-50%), and 40% specifically had the *lowest* max drift (7.38) of the whole grid, with the least-favorable individual photo's `leaf_frame_fraction` at 0.046 — comfortably clear of the 0.02 floor. The dataset's remaining noise (max drift still bounces 7-15 points across void levels) traces to a specific, repeatedly-observed pattern, not a void-cap problem: low-severity photos near the `minimum_disease_fraction` censoring threshold are inherently unstable, because PDLA is a ratio with a small numerator there, so small absolute pixel changes cause large relative swings — see the Known Limitations note below. Two of the 50 raw photos gathered for this measurement were excluded first: 2 stock-photo screenshots whose visible watermark text crossed directly over the lesion area, and 2 more whose baseline `leaf_frame_fraction` (0.039 and 0.405) was far enough from anything achievable through the app's own alignment modal that using them as a "before any void" reference point would have measured compounding-error-from-a-bad-starting-point rather than actual void tolerance.

**Location is plant-level and resolved once**, same as before, just timed around the alignment step instead of around selection. The farmer walks around one plant taking several shots, so re-fixing GPS per photo would jitter the pin. For a camera batch, the GPS fix is requested the moment photos are picked (overlapping alignment time, rather than waiting for it) and applied when the first photo of that batch is confirmed. For a gallery batch, EXIF is read from the first *confirmed* photo's original file, not the first *selected* one — skipping a photo in the aligner correctly excludes its EXIF from setting the plant's location. Either way, coordinates already set are never overwritten by a later photo, and a manual edit always wins as the provenance of record (`locationSource: 'manual'`).

Adding a photo **appends** to the current plant — it does not start a new one. "Save Plant" commits the node and clears the draft; "Discard plant" (behind a confirmation dialog) throws it away. Removing the last photo discards the draft too.

**Blob lifetime:** draft photos are `URL.createObjectURL` blobs (the lightbox needs full resolution). On commit they are downscaled to small data URLs via `makeThumbnail.js` and the object URLs are revoked. Object URLs must never outlive a draft — 50 plants × up to 10 full-resolution photos would otherwise stay pinned in memory on the mid-range Android this targets.

Mask previews (`masks` on each committed photo) are a copy-through exception to that lifecycle, not an addition to it: the backend ships them already downscaled to `MASK_PREVIEW_MAX_SIDE`, so the committed allow-list (`App.jsx`'s `handleAddSample`) copies the string verbatim with **no re-encode, no object URL, and no new revoke site** — `masks` is immutable, unlike `image.thumbnail`. Because a draft photo's mask viewer still points its "aligned photo" pane at the draft's live object URL, `App.jsx` closes the viewer (`setMaskViewer(null)`) at every site that revokes one — remove-photo, discard-draft, and commit — so it can never show a broken image after a teardown it wasn't watching for. `THUMBNAIL_MAX_EDGE` (`makeThumbnail.js`) is 384px, not 192px — raised so a committed photo still reads clearly in the PDF report's three-pane row next to its 256px mask previews (see PDF Report Export below) — so the committed sample store's worst case is now ~15 MB at the 50×10 ceiling, not ~5 MB.

## PDF Report Export

`src/utils/exportReport.js`'s `exportFieldReport()` builds a self-contained PDF record of a survey session, client-side, via **jsPDF** (the one addition to the otherwise-locked toolstack — see Toolstack & Constraints above). Triggered by the "Export PDF Report" button in `ActionPanel`'s Step 3 card, visible only once `heatmapData` exists. It drives the same `isProcessing`/`loadingMessage`/`loadingProgress` overlay as `handleGenerateHeatmap` in `App.jsx` — a 50-plant × 10-photo session walks ~500 images, so the export loop yields to the event loop once per plant (`exportReport.js`'s `yieldToUi`) rather than running as one synchronous block, or the mid-range Android this app targets would appear frozen.

**Page structure:** a cover page (field area via `turf.area`, plant/photo counts, field-wide disease breakdown, a "Reading this report" note block, and a Phase 2 class legend sourced from the first available photo's `masks.class_order`/`palette`/`class_names` — never a hardcoded class list, preserving the same "no client-side class knowledge" property the live `MaskInspectorModal` legend has); one page per plant, in order (per photo: aligned → Phase 1 mask → Phase 2 mask, then that photo's diagnosis line; then the plant's pooled summary — Total affected / Diseases found / Photos used, matching `SamplePanel.jsx`'s wording exactly — then coordinates); then one page per heatmap layer that exists in the field. A photo with `usable === false` is still shown, badged `EXCLUDED`, never silently dropped — this is a survey record, not a highlight reel. Every number and caption is read from the same committed-sample fields and formatted with the same conventions the on-screen UI already uses (`.toFixed(1)` + `%` for severities, `.toFixed(6)` for coordinates, `parseFloat(...).toFixed(2)` for confidence) — this file does not maintain a second source of truth for any of them.

**The heatmap figures are composited offscreen** (`src/utils/renderFieldFigure.js`), not screenshotted from the live Leaflet map — there is no map ref threaded up to `App.jsx` (only child components call `useMap()`), and a screenshot would tie the report to whatever the user happened to be looking at rather than a canonical, reproducible view. Esri's tile endpoint sends `Access-Control-Allow-Origin: *` (verified against the live server), which is what makes `crossOrigin: 'anonymous'` tiles paintable onto a canvas that can still be read back with `toDataURL()`. Vector elements (boundary stroke, numbered sample pins) are placed in true Web Mercator to register exactly against the tiles; the SES raster itself is still painted in the *linear* lat/lng space `heatmapRaster.js` has always used (see below) and stretched into the Mercator bbox rect — the same simplification `L.imageOverlay` already makes for the on-screen map, and at this app's field sizes (tens to a few hundred meters) the chord error between linear and true Mercator latitude is on the order of 1e-3 px, well under one pixel. The figure must never reject — a failed or timed-out tile fetch (bounded by a per-tile timeout and a whole-mosaic wall-clock budget) falls back to a plain background so an offline export still produces a usable PDF, and a canvas-taint retry (repaint with zero tiles) guards against a proxy or cache defeating the verified CORS header.

**The rasterizer is shared, not duplicated.** `src/utils/heatmapRaster.js` holds the SES-grid-to-canvas painter extracted verbatim from what used to be inline in `HeatmapOverlay.jsx` — the live map overlay and the offscreen PDF figure both paint from this one module, so a change to the color LUT or the boundary-clip logic can't drift between what the farmer sees on screen and what ships in the report.

**PDF figures are not the model's full-resolution output.** They're built from the committed sample's stored 384px thumbnail and the backend's 256px mask previews — the original 1024px aligned crop is revoked at commit time (see Blob lifetime above) and cannot be recovered at export time, however long after commit the export happens.

## Known Limitations (Prototype Scope)

- Disease classification covers 5 classes only (no Sheath Blight) — limited by the trained Phase 2 checkpoint, not the code.
- Requires the FastAPI backend running locally (`backend/server.py`); there is no hosted inference endpoint.
- No user authentication or data persistence (state is in-memory only).
- No offline tile caching (no Service Worker).
- Single-field session only (page reload resets everything).
- IDW computation caps at ~50,000 grid cells for browser performance.
- Max 50 plant nodes per session, max 10 photos per plant.
- **Phase 1 cannot reject non-rice subjects.** It has no negative class, so a photo of soil, a hand, or sky still yields a leaf mask and a PDLA. The plausibility band in `constants.js` reduces obviously-bad input but is not a rice-leaf detector, and cannot become one without retraining with a negative class. The alignment crop doesn't change this — it fixes framing, not subject matter.
- **The blade-width guide is advisory, and pooling weights are blade-width-normalized rather than biologically calibrated** — see Plant-Level Pooling above. Nothing measures whether a photo's leaf actually fits the rail, so pixels still can't be converted to mm² without a physical scale reference in frame; a photo that ignores the guide entirely is still accepted and pooled the same as one that follows it precisely. Showing the guide live in `CameraCaptureModal` narrows the gap between "advisory" and "followed" but does not close it — the live guide is still purely visual, same as the aligner's.
- **The live in-app camera needs a secure context and silently falls back over plain HTTP.** `cameraSupport.js`'s `supportsLiveCamera()` requires `window.isSecureContext` — the LAN `http://<lan-ip>:5173` address the README suggests for phone testing against the local Vite dev server is not one, so the Camera button falls back to `<input capture="environment">` there with no error shown; only a deployed HTTPS build (or a tunnel) exercises the live-viewfinder path end-to-end.
- **The aligner's default crop box lands exactly on the live-framed region after a camera capture, but this is a derived property, not an enforced one.** `CameraCaptureModal`'s `handleShutter` captures the centered SQUARE of the viewfinder stage's shorter side (not the full ~9:16 visible rectangle, and not just the pixels inside the framing rectangle either) — the same square the live guide box sits inside of, concentrically, at `ALIGN_STAGE_INSET_FRACTION`. Because `react-easy-crop` fits a square source image via `objectFit: "contain"` against the OUTER stage container (not `cropSize`) at zoom 1, and `cropSize` is that same `ALIGN_STAGE_INSET_FRACTION` of the same container's own `min(width, height)`, the ratio between the two is always `ALIGN_STAGE_INSET_FRACTION` regardless of how the aligner's own stage differs in size from the camera's (it has more chrome, so it's shorter) — see the derivation in `handleShutter`'s own comment. So a well-aligned shot needs no zoom/pan at all; the ~8% margin the square captures beyond the guide box is what a farmer can still nudge into if the framing was slightly off. This depends on `useFramedStageSize` staying the single source of both modals' framing geometry, and on `ImageAlignmentModal`'s `zoom` state continuing to default to `1` (`ImageAlignmentModal.jsx`, reset per photo) — if either changes, re-derive this rather than assume it still holds.
- **There is no re-align action.** The original file isn't retained past a successful crop (ten originals pinned for one draft would blow the memory budget the `MAX_IMAGES_PER_SAMPLE` comment already worries about), so fixing a bad alignment means removing the photo and retaking it.
- **IDW weights every node equally** regardless of how many photos back it. A node from one blurry photo influences the surface as much as one from ten; `leafPixels` is recorded on each sample if this is ever revisited. This now applies **independently to each of the four surfaces** (General plus the three disease layers) — a node's influence isn't diluted or concentrated differently on one layer versus another, but the underlying equal-weighting limitation is unchanged on all of them.
- **A single photo showing two diseases at once is attributed ENTIRELY to its dominant diagnosis** — a secondary disease visible in that one photo is invisible to `diseaseFindings` unless some *other* photo of the same plant was itself diagnosed with it (see Plant-Level Pooling above for why `diseaseSeverity` rows sum exactly to `severity`). Multi-disease reporting is therefore only as fine-grained as the farmer's photo-taking, not as fine-grained as the pixels within a single photo.
- **The General Threat heatmap layer is `Math.max()` of SES classes, not a percentage** — see IDW Parameters above. Never label it with a `%` sign or average it with per-disease PDLA values.
- **IRRI SES breakpoints are applied as documented by IRRI, not re-validated against this checkpoint's own PDLA distribution.** The banding in `sesScale.js` assumes the trained Phase 2 model's disease-pixel counting is comparable enough to IRRI's original visual-rating methodology to reuse its numeric breakpoints as-is. That assumption is untested here.
- Per-photo `confidence` is a mean softmax posterior over pixels, **not a calibrated probability** that the diagnosis is correct. State that caveat wherever it is surfaced.
- **No guaranteed background margin** — see the Leaf Plausibility Guard's Post-crop note above. Re-measure `leaf_frame_fraction` against real field captures and be ready to raise `MAX_LEAF_FRAME_FRACTION` before either bound is quoted in the thesis.
- **The overflow void-fill cap and fill color are measured on one 48-photo sample** (`backend/probe_fill.py`, 2026-07-29 — see Sample Acquisition Methods above for methodology). `ALIGN_MAX_OVERFLOW_FRACTION` (0.40) and `ALIGN_VOID_FILL_RGB` (flat black) should be re-run if the Phase 1 checkpoint changes or a larger field set becomes available.
- **PDLA is unstable for low-severity photos near the `minimum_disease_fraction` censoring threshold**, independent of void/overflow entirely — this has now shown up in three separate photos across three separate measurement runs (small-disease-area leaves whose severity swings by double digits or fully censors to 0 from small absolute pixel changes). It's a property of PDLA being a ratio with a small numerator near a hard censoring cutoff, not a void-cap defect, and not something a bigger dataset will smooth away. Worth flagging explicitly if the thesis reports PDLA confidence/precision for low-severity cases.
- **PDLA drift is systematically downward as void increases**, and two photos of the same plant taken at very different void levels are not perfectly comparable even though both pass the overflow gate — a real cost of the looser 40% cap versus the original 20%, not just measurement noise.
- **The mask preview is a 1/4-scale NEAREST subsample (see Mask Previews above) — not evidence for the PDLA number**, which is computed from `class_pixels` at full WORK resolution before any preview is built; isolated few-pixel lesions may be decimated away in the preview despite being counted in the real measurement. A block-max-pooling step that would preserve tiny lesions in the preview was considered and rejected — it would insert an undocumented second transform between model and viewer and systematically over-state disease relative to the reported PDLA.
- **Phase-2 mask-preview colors are a display palette invented for this viewer, encoding class identity only** (see Mask Previews' Palette note above) — unrelated to the green→red SES ramp in `sesScale.js`. A red region in the mask means "this class was predicted here," never "this point is severe."
- **The PDF report's photo panes are built from stored thumbnails and mask previews, not the full 1024px aligned crop** — see PDF Report Export above. The original is revoked at commit time and cannot be recovered at export time, however long after commit the export happens.
- **The PDF heatmap figures are re-rendered from the SES grid, not a screenshot of the live map.** They can disagree with the on-screen map by a small, pre-existing amount: `idwWorker.js` computes `cols`/`rows` via `Math.ceil`, so the grid can span up to one cell (`IDW_CELL_SIZE_METERS`, default 2m) more than the boundary's bbox, while both `HeatmapOverlay` and the PDF figure paint that grid across the bbox's exact extent — a sub-cell compression that is invisible on screen but can show as a thin misregistration fringe at the field's far edge in a large, high-resolution print. Both render paths share the same rasterizer (`heatmapRaster.js`), so this affects them identically; it is not specific to the PDF.
- **LOOCV inherits the worker's degree-space Euclidean distance metric** (see IDW Parameters above) — no cos(lat) anisotropy correction is applied inside `idwCore.js`'s distance calculation, only to grid spacing, so E-W separations are under-weighted relative to true ground distance by ~1/cos(lat) (≈3.7% at 15.5°N). This is correct for validating the model *as shipped*, but the reported MAE/RMSE should never be described as error against true metric distance without stating this.
- **LOOCV measures interpolation skill at sampled locations only** — not SegFormer classification accuracy (that's a separate question the mask-inspector/PDF pipeline doesn't validate either), and not accuracy in the field interior where sampling is sparsest, since every held-out point is, by construction, a location that already had a real measurement.
- **LOOCV scores edge nodes pessimistically.** A held-out point on the sampling layout's convex hull is extrapolated from one side only (its neighbors are not evenly distributed around it the way an interior point's are), so MAE/RMSE trend conservative for compact layouts and the effect grows with a sparser or more elongated field.
- **Coincident or near-duplicate coordinates make LOOCV look artificially perfect.** IDW is an exact interpolator (see `idwCore.js`'s `dist < 1e-10` branch), so a held-out point sharing coordinates with another sample gets that twin's value back verbatim regardless of how wrong it would be elsewhere — check for duplicate `lat`/`lng` pairs before quoting a LOOCV figure from a session where the same spot may have been sampled twice.
- **A `degenerate` channel (see IDW Parameters above) reports zero error, not zero interpolation error** — a disease absent from every node, or present at only one, has no variance for LOOCV to fail at predicting. Report it as "no signal to validate," never as evidence of accuracy.
